# 拍照与录像的实时左右纠正

续接提交 026f964，保留两 agent 的媒体发布检查与 JPEG 检查恢复修复。本轮首先完成用户指定的实时取景方向，再推进防抖与影像算法。

## 实际验收

V2256A、Android 14、原 ROM、真实 CLOSED、display 1、无 device-state override。

- 自有 DUMP 保护广播已收到真实 UID 2000 的工作者 Binder，解决本 ROM 上 Shizuku 管理器外部提供者无法访问导致的连接超时。
- 原生拍照取景区域已连续左右纠正，计数从 6 增至 631；日历“31”正常可读，画面持续更新。
- 按原生快门后，确认页进入 waiting_preview_controls，预览覆盖层透明，不对已正向的成片再次翻转。确认正常返回并保存原图。
- 同一工作者取消拍照后进入录像；修复系统显示库重复加载后，录像待机计数持续增长，录制中从 359 增至 364，画面方向正确。
- 录像计时提示位于取景内，单独保留其原生方向。最终约 5 秒 MP4 为 2,348,489 bytes，正常返回 Movies/XFlipCamera 并解码显示，覆盖层服务停止。
- 实测期间客户端为 0.2.3，Shell 工作者迭代到 0.2.6；完整单一版本 APK 的最终安装复验另行记录，不能把混合调试会话直接称为发布包验收。

真实场景照片、视频和完整截图不公开上传。上述计数与状态是服务实际 dump，像素方向通过原生画面与确认/返回页对照，不以编译或服务连接代替图像验收。

## 修复与限制

工作者取消使用独立 generation，避免旧线程 finally 改写新会话；同一 Surface 只发起一次 START，SurfaceDestroyed 明确 STOP。缓存 Android 14 的显示控制类，防止二次加载 native library 失败。

捕获使用逻辑显示坐标和排除自身图层；快门状态按右侧控制区域的实际颜色与边界识别，不依赖假定 DPI。确认页的白色按钮不会触发预览纠正。此检测仍需后续覆盖更多 ROM/主题和异常弹窗。

透明度限制由不可触摸覆盖层触发；现在取景覆盖层完整显示，快门与确认在其外侧可操作。取景区域的原生点击对焦暂被覆盖层占用。照片按 4:3、视频按 16:9 的外屏布局验证，其他比例、方向、内屏与折叠切屏仍待验收。

录像计时区域保留原生像素，有一小块背景拼接，当前为实验显示方案。输出照片和视频由 vivo 系统相机直接生成，预览纠正不修改原始成片，不包含 Google 专有算法。

## 启动

本机 Shizuku 用户服务启动仍受 ROM 内容提供者访问限制，采用真实 Shell 的直接 Binder 通道。安装后保持合盖，在外屏打开“外屏系统相机”，允许本应用悬浮窗，再在电脑运行：

```powershell
powershell -File scripts/start_preview_bridge.ps1 -Serial YOUR_DEVICE_SERIAL -Adb PATH_TO_ADB
```

确认日志有 preview_worker_started uid=2000；在相机入口勾选“系统预览左右纠正”，再点拍照或录像。桥接进程采用 nohup，可脱离当前 ADB shell；重启手机或相机进程丢失 Binder 后需要重新启动。启动脚本的断线/恢复验证仍待完成，不能宣称无需电脑初始化。

原有外屏助手对普通 Activity 的启动仍有影响，保留用户设置。没有修改系统密度、镜头权限或系统签名。

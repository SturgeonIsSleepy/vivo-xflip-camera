# NLM 调度同包对照与交付

续接58fcf5a和前两天的滚动行缓存、原图保留、同窗口编辑工作。本轮只优化可选拍后NLM耗时，交付0.4.4-lab / 30，手机仍只有org.codeaurora.snapcam.lab。生产块从512改为768，OpenCV线程从2改为4；h5、模板7、搜索21、halo16、色彩处理和JPEG97不变，默认仍关闭。

## 方法及结果

合盖ARM64实机、3072×4096固定合成JPEG。先用同一个试验APK按正序/逆序测五组调度，每组两次，计时仅NLM，排除解码、像素摘要和JPEG编码。十份原始ARGB像素摘要一致。

| 块 / 线程 | NLM两次耗时ms | 中位ms |
| --- | --- | ---: |
| 512 / 2 | 18403、32039 | 25221 |
| 512 / 4 | 20330、32258 | 26294 |
| 768 / 4 | 12813、26808 | 19810.5 |
| 1024 / 2 | 21380、29917 | 25648.5 |
| 1024 / 4 | 15492、21061 | 18276.5 |

1024/4在这组中位更快，最终选768/4以限制缓存增长，未声称它是全场景最优值。仅加线程的512/4没有明显收益。[OpenCV 4.12官方实现](https://github.com/opencv/opencv/blob/4.12.0/modules/photo/src/denoising.cpp)按图像面积设置parallel_for_粒度，因此小块可能限制任务并行度；这是源码推断，性能判断仍以实测为准，未复制该C++实现。

随后在最终APK内，以相同生产save事务做ABBA对照：A显式512/2，B使用生产默认768/4。四次均无内存采样，计时包含解码、NLM、JPEG/EXIF和发布。

| 顺序 | 配置 | 完整保存ms |
| --- | --- | ---: |
| 1 | A 512/2 | 20429 |
| 2 | B 默认768/4 | 15393 |
| 3 | B 默认768/4 | 26366 |
| 4 | A 512/2 | 53364 |

A中位36896.5ms，B中位20879.5ms，样本算术降幅43.4%。运行漂移非常大，样本少、温度与频率未固定，不能作为固定43%提速承诺，也不能把昨天不同APK的单次时间拿来做基线。试验报告的thermal状态均0，只代表Android状态读数，不能据此证明没有降频。

## 内存及质量边界

另各跑一次内存采样，不混入上面的耗时中位。dumpsys meminfo每次等待0.5秒再加命令延迟，覆盖准备和测试；只统计.lab进程，排除系统相机和Shell桥接。离散观测峰值是下界，可能漏短尖峰，各列峰值不一定同时。

| 项目 | 512/2 | 默认768/4 |
| --- | ---: | ---: |
| 观测PSS峰值KiB | 139100 | 148378 |
| RSS峰值KiB | 249060 | 259476 |
| Native Heap allocated峰值KiB | 96495 | 96577 |
| Java Heap allocated峰值KiB | 12196 | 17936 |
| 有效样本数 | 59 | 46 |
| 带采样保存ms | 44500 | 39858 |

本组PSS增加9278KiB，约9.06MiB。理论源行缓存由6.375增至9.375MiB，不能把理论缓存差直接当成进程增加量。相对历史整图副本实现仍保留滚动窗口，但不以跨会话内存数值做严格因果比较。

四份ABBA加两份内存采样保存结果独立解码，六份最大通道差均0；小图与独立整图NLM差0，噪声MSE比0.3676296、平坦噪声标准差比0.4594235、文字边缘比1.0001129。调度优化没有声称提高画质；单个合成图也不能证明所有真实场景的质量。

## 实机交互与检查

最终包合盖预览及直方图正常，同窗口打开实际新拍照片，开启NLM预览、另存处理中按Back取消。没有新增媒体行，最后保存引用及原图字节不变，编辑器可重新打开。真实照片、文件名、摘要和EXIF只留本地，公开数据仅合成图与软件信息。本轮不扩展录像、防抖、Google Camera或真正多曝光HDR的成功声明。
